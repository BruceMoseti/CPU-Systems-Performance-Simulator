gprof flat profiles of the simulator itself, replaying traces/matrix_naive.trace
(21.3M records) on an Intel Xeon at 2.4 GHz.

Reproduce with:
  cmake -S . -B build-profile -DCMAKE_BUILD_TYPE=Release \
        -DCMAKE_CXX_COMPILER=g++ -DPERFSIM_PROFILE=ON
  cmake --build build-profile -j
  cd /tmp && ./build-profile/perfsim --config configs/baseline.json \
        --trace traces/matrix_naive.trace --quiet
  gprof ./build-profile/perfsim gmon.out

Note that -pg adds per-call instrumentation, so absolute ns/call figures are
inflated. The ranking and the relative change are what matter.

Three findings:
  1. Cache::access dominates. Line state was an array of 24-byte structs, so an
     8-way tag scan strided across three host cache lines.
  2. Cpu::access spent its time scanning all 16 MSHRs linearly to find the entry
     that frees up soonest. 14.2M misses x 16 entries.
  3. refill() was called 120.8M times: once per character of the trace, roughly
     5.7 characters per record.

Total profiled time fell from 0.66 s to 0.25 s. Per-call self time:
  Cache::access   12.58 -> 2.33 ns  (parallel arrays: one host cache line per scan)
  Cpu::access     10.54 -> 3.52 ns  (binary min-heap instead of a linear scan)
  trace parsing    ~8.0 -> 5.63 ns  (buffer once per record, not per character)

Text parsing is now the largest single cost. The next step would be a binary
trace format, which is a format change rather than an optimisation of existing
code, so it is left undone.
